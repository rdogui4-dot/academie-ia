Académie IA Générative — 3 octobre 2026

STATUT
Ce rapport porte sur le code de la branche principale récupérée au commit
b8b3d9cbab76537d2d9dd96475608b1718d5f4c5 et sur les quatre manuels privés
fournis précédemment. Les corrections sont préparées et testées localement.
Elles ne sont pas encore appliquées à votre Supabase ni publiées sur GitHub.
Aucun compte apprenant réel n’a été modifié pendant ces tests.

1. RÉSULTAT DU CHECKUP

A. Validation des étapes — anomalie majeure corrigée dans le paquet
Avant : une case cochée et une écriture directe dans la progression pouvaient
suffire ; le serveur n’exigeait ni carnet renseigné, ni lecture complète,
ni remises distinctes. Le blocage de navigation se faisait surtout à l’écran.
Correction : toute écriture de progression passe par des fonctions contrôlées.
Une étape nécessite les précédentes, un carnet personnel d’au moins 80
caractères, la déclaration de lecture de chaque page et toutes les remises.
Une remise exige de 120 à 30 000 caractères. Les travaux demandés à nouveau
par le formateur doivent être corrigés. Le minimum de longueur sert uniquement
à refuser une réponse vide, et ne démontre pas la qualité pédagogique.

B. Accès à l’évaluation — anomalie majeure corrigée dans le paquet
Avant : le projet pouvait être remis sans terminer le parcours ; le serveur
exigeait un projet et une inscription active pour noter, sans exiger l’ensemble
des activités. Correction : le projet final reste verrouillé tant que toutes
les étapes, pages, carnets et remises ne sont pas complétés. Le dossier final
exige de 200 à 30 000 caractères. Les erreurs sont renvoyées par Supabase,
même si un utilisateur contourne l’interface.

C. Correction et certification — renforcées dans le paquet
Toutes les remises doivent être acceptées par un formateur habilité avant
l’enregistrement de la note finale. L’espace formateur affiche les carnets,
les consignes, les réponses et les éléments manquants. Il permet d’accepter
une remise ou de demander une correction avec un retour explicatif.
Le serveur refuse de corriger une version devenue obsolète. La note finale
archive un instantané des remises, carnets et déclarations de lecture.
Modifier un carnet ou une remise invalide l’étape et les suivantes, et invalide
le certificat du niveau jusqu’à une nouvelle évaluation. Modifier le projet
final invalide également ce certificat. Une nouvelle correction est nécessaire
pour une remise modifiée, même si elle avait été acceptée.

D. Téléchargements — blocage préparé côté serveur
Avant : un apprenant inscrit pouvait récupérer le PDF, les slides PDF/PPTX
et le corpus complet depuis le stockage privé. Retirer un bouton ne suffisait
pas à interdire l’accès direct. Correction : une politique restrictive du
stockage bloque les fichiers originaux pour les rôles anonymes et connectés.
Seuls le fichier de présentation du cours et les pages de lecture WebP/TXT
restent lisibles, sous réserve du droit d’accès au niveau. Le bucket reste
privé. Les boutons PDF/PPTX et le lecteur PDF sont retirés du site.
Le manuel est consultable page par page avec une version texte accessible ;
les slides restent consultables en ligne. Le carnet personnel reste exportable
au format TXT. Les clés serveur administratives gardent leurs droits : elles
ne doivent jamais être placées dans le site ou communiquées à un apprenant.

LIMITES : afficher un contenu dans un navigateur ne peut empêcher toutes
les captures, l’impression, la copie du texte ou l’enregistrement d’images.
Le blocage vise la distribution des originaux PDF/PPTX, pas une protection
absolue contre toute copie. Les anciens téléchargements, copies, caches et
versions historiques du dépôt ne peuvent pas être retirés à distance.
Les anciens liens signés éventuels peuvent conserver leur validité jusqu’à
leur expiration ; le nouveau lecteur ne crée pas de liens signés.

E. Lecture intégrale — obligatoire, mais déclarative
Les 201 pages sont affectées aux étapes, sans trou ni doublon de couverture.
L’apprenant déclare la lecture de chaque page. L’interface attend le chargement
de la page avant d’autoriser cette déclaration. Le serveur exige toutes les
déclarations. Ni une case, ni un temps d’affichage ne prouvent qu’un texte a
été compris. La vérification de compréhension reste fondée sur les productions
et leur examen par le formateur. Il n’y a pas de dispositif de surveillance.

F. QCM — distinction nécessaire entre entraînement et examen
Les manuels contiennent des questions avec leurs réponses visibles. Ils
conviennent à l’auto-évaluation, pas à un examen secret. Le site ne possède
pas actuellement de banque de questions confidentielle, de tirage aléatoire,
de chronomètre d’épreuve ni de correction automatique sécurisée.
Le formateur organise donc l’épreuve finale supervisée, puis saisit les notes.
La présentation du site utilise désormais des POINTS de barème plutôt que
promettre un nombre de questions que l’application ne distribue pas.
La conception d’une nouvelle banque d’examen est un chantier distinct ; elle
n’a pas été inventée ni présentée comme opérationnelle dans cette livraison.

2. BARÈMES VÉRIFIÉS ET CONSERVÉS

N1 : connaissances /40, minimum 28 ; projet /60, minimum 42 ; total >=70/100.
N2 : connaissances /30, minimum 21 ; projet /70, minimum 49 ; total >=70/100.
N3 : connaissances /40, minimum 28, converties sur 30 pour le total ;
     projet /70, minimum 50 ; total >=70/100.
N4 : connaissances /30, minimum 21 ; projet /70, minimum 50 ; total >=70/100.

Les seuils séparés restent obligatoires : un excellent projet ne compense pas
une note de connaissances sous le minimum. Seul le formateur peut attribuer
les notes. L’inscription doit être active et l’adresse du compte confirmée.
La lecture et les activités seules ne délivrent jamais de certificat.

Le catalogue comprend les 41 activités existantes et 57 exigences distinctes

Toutes ces remises sont obligatoires. Cela inclut l’ensemble des cas métiers

aux remises ; il ne les remplace pas.
Les réponses peuvent décrire une production, ses résultats et ses preuves,
avec des liens autorisés si nécessaire. Aucun dépôt de pièces jointes n’a été
ajouté. Le formateur doit vérifier les éléments cités ; un lien seul ne suffit
pas à démontrer le travail.

4. INCOHÉRENCES PÉDAGOGIQUES À CONNAÎTRE

- N1 : le sommaire annonce notamment un atelier de génération d’images et un
  cas de brainstorming qui ne disposent pas d’un développement aussi explicite
  dans le corps du support. Deux consignes complémentaires sont ajoutées au
  catalogue et identifiées comme compléments ; elles ne sont pas présentées
  comme des passages déjà présents dans le manuel.
- N2 : le numéro 2.7 est utilisé pour deux exercices différents. Le catalogue
  distingue l’audit de sécurité et le pipeline RAG par leurs titres et identifiants.
  Le PDF d’origine n’est pas réécrit dans cette livraison.
- Les supports conservent des intitulés de certification et des formulations
  historiques. Certaines mentions de reconnaissance ou de durée de validité
  ne constituent pas une preuve d’accréditation. Le site indique qu’aucune
  reconnaissance externe n’est revendiquée. Une harmonisation éditoriale des
  manuels reste à faire avant toute promesse commerciale de ce type.
- Le titre historique du corpus N1 et certaines références à « Prompt
  Engineering » ne correspondent pas toujours au nouvel intitulé du parcours.
- Les durées annoncées doivent être harmonisées entre supports et catalogue,
  notamment N4. La présente livraison ne modifie pas arbitrairement les durées.
- L’ancien circuit Apps Script de certificats, s’il est toujours déployé,
  doit être retiré ou rendu inaccessible séparément. Les protections Supabase
  ne ferment pas automatiquement un ancien déploiement Google indépendant.

5. EFFET SUR LES DONNÉES EXISTANTES

Les inscriptions, carnets, remises finales et résultats existants sont gardés.
Les étapes cochées sous l’ancien système restent dans la base avec leur version
historique, mais ne satisfont pas les nouvelles obligations. L’apprenant voit
son carnet et complète les exigences manquantes avant de revalider les étapes.
Les certificats déjà émis ne sont pas tous révoqués par la migration. Ils ne
prouvent donc pas rétrospectivement le respect du nouveau dispositif. En cas
de modification de leur dossier, les règles de revalidation décrites plus haut
s’appliquent. L’Académie doit distinguer les sessions anciennes des nouvelles.
Les formateurs habilités peuvent lire les carnets pour l’évaluation ; le texte
d’information du site le précise. Les carnets ne sont pas envoyés au tuteur IA.

6. VÉRIFICATIONS EFFECTUÉES

- Exécution des migrations 001 puis 002 dans PostgreSQL embarqué (PGlite),
  avec représentations locales d’Auth et Storage.
- Sept groupes de contrôles du nouveau dispositif, parcourant les quatre
  niveaux : 41 étapes, 98 remises et 201 déclarations de lecture.
- Refus des sauts d’étape, des réponses trop courtes, de l’écriture directe de
  progression/projet, de l’accès anonyme et de la lecture d’un autre dossier.
- Refus des originaux PDF/PPTX/corpus même en présence d’une politique
  permissive supplémentaire ; pages permises au niveau actif ; accès refusé
  après suspension.
- Refus du projet incomplet et de la note avant acceptation des remises ;
  seuils testés ; snapshot conservé ; modification invalidante et contrôle
  des versions de correction testés.
- Treize scénarios du schéma initial également réussis, séparément, pour
  conserver une référence sur les inscriptions, certificats et seuils.
- Sept tests du frontend public réussis ; 22 pages HTML et 255 liens locaux
  vérifiés ; aucun lien local cassé, identifiant HTML dupliqué ou conflit Git.
- Syntaxe JavaScript et Python contrôlée ; correspondance entre les identifiants
  des interfaces et les éléments HTML vérifiée.
- 201 images de pages décodées ; contrôle visuel ponctuel de pages rendues.
  Aucun manuel PDF, PPTX, corpus ou migration SQL n’est inclus dans dist.

LIMITES DE VÉRIFICATION : pas de test sur la base Supabase de production,
pas de test SMTP supplémentaire, pas de véritable examen avec un apprenant.
Le test visuel interactif navigateur n’a pas pu être effectué ici : le
navigateur de test n’a pas pu être installé. Une recette après publication
reste nécessaire, sur ordinateur et téléphone, avec comptes apprenant et
formateur. Les vérifications locales ne sont pas un audit de sécurité exhaustif.

7. MISE EN PLACE — ORDRE À RESPECTER

Lire INSTALLATION.txt fourni dans le ZIP.
1) Extraire le paquet complet.
2) Préparer la branche locale avec PREPARER-EVALUATIONS.ps1 : sauvegarde Git,
   intégration et vérification, sans publication.
3) Importer les 402 fichiers WebP/TXT (deux fichiers par page) dans le bucket
   academy-private, au moyen du script fourni et de votre clé serveur saisie
   localement. Garder le bucket PRIVÉ. Les PDF/PPTX existants ne sont pas effacés.
4) Dans Supabase SQL Editor, exécuter UNIQUEMENT la nouvelle migration 002,
   une seule fois. Ne pas réexécuter la migration initiale 001.
5) Publier la branche préparée vers main puis lancer le workflow GitHub Pages.
6) Vérifier la recette décrite dans INSTALLATION.txt.

Prévoir un court créneau sans apprenants entre l’étape 4 et la fin du déploiement :
l’ancien lecteur ne fonctionnera plus lorsque les originaux seront interdits.
La sauvegarde Git ne sauvegarde pas Supabase : conserver une sauvegarde des
données de production selon les moyens disponibles dans votre projet avant
l’application de la migration. Aucune clé secrète ne doit être copiée dans Git.
